# Session Retrospective — 2026-07-24

**Date:** 2026-07-24  
**Session Type:** Incident Retrospective — Sub-Agent File Permission Bug  
**Context:** Frontend implementation (Sidebar.tsx, TopHeader.tsx, useSidebar.ts) via multi-agent orchestration  
**Participants:** Orchestrator (AI), Sub-Agents (AI), User

---

## What Went Wrong

Sub-agents created frontend source files (`Sidebar.tsx`, `TopHeader.tsx`, `useSidebar.ts`) with file permission `600` (owner-only read/write) instead of the expected `644` (world-readable). When Vite dev server attempted to read these files from inside the Docker container — running as user `node` — it failed with an `EACCES: permission denied` error. The error surfaced on the login page after deployment, blocking the user from using the application.

---

## Root Cause

The `write_file` tool, when invoked by sub-agent processes, creates files with umask `077`, resulting in `600` permissions. Meanwhile, the Orchestrator's verification checks (TypeScript compilation `tsc` + ESLint) ran on the **host** as the host user — which owns the files and therefore can read them without issue. Both checks passed.

However, the Docker container runs as user `node`, a **different user** from the host user that owns the files. Since the files were `600`, user `node` could not read them, causing Vite to crash at runtime with `EACCES`.

**Summary of the gap:**
- File creation: umask `077` → permission `600`
- Verification: host user owns files → `tsc` + `ESLint` pass
- Runtime: container user `node` → `EACCES` permission denied

---

## Impact

- **User-facing:** User encountered `EACCES` error on the login page after deploying the frontend changes.
- **Functional:** Blocked all usage of the application — the login page is the entry point.
- **Time cost:** Required manual debugging of file permissions, identification of the umask issue, and manual `chmod` to restore.
- **Trust:** The Orchestrator reported "verified" status, but the bug still reached runtime — undermining confidence in the verification process.

---

## Lesson Learned

1. **Verification environment ≠ Runtime environment.** Passing `tsc` + `ESLint` on the host does not guarantee the files will be readable in the container. The verification must match the runtime conditions.
2. **TSC + ESLint alone are insufficient.** These checks validate code correctness but do not validate file-system-level accessibility. Permission and ownership checks are a separate concern.
3. **Sub-agent file creation has side effects.** Tools that create files may do so with restrictive permissions due to process umask — this must be explicitly checked, not assumed.

---

## Prevention

Adopt the **Orchestrator Evaluation Checklist** as a mandatory verification gate before reporting task completion:

| # | Check | Command | Purpose |
|---|-------|---------|---------|
| 1 | TypeScript compilation | `npx tsc --noEmit` | Code correctness |
| 2 | ESLint | `npx eslint .` | Code quality |
| 3 | File permissions | `ls -la <files>` | Confirm `644` (not `600`) |
| 4 | Container readability | `docker exec <container> cat <file>` | Verify runtime user can read files |
| 5 | Runtime smoke test | Hit the endpoint in the browser / `curl` | Confirm no runtime errors at the app layer |

All five checks must pass before the Orchestrator marks a task as "verified."

## Key Takeaways

1. **Trust nothing the verification doesn't actually test.** If the container user never touched the file during verification, the file was not verified for runtime.
2. **Permission checks are cheap and catch expensive bugs.** A single `ls -la` and `docker exec cat` takes seconds and would have caught this issue immediately.
3. **The checklist grows with each incident.** R6 exists because R1–R5 didn't catch this class of bug. Every retrospective should evaluate whether the checklist needs a new entry.
